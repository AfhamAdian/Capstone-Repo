# backend/db/

Database schema and migrations, in one place.

## Layout

```
db/
  schema/            Current-state reference, one file per table, named after
                      the table it describes. Context-only - not meant to be
                      run (each file carries that warning as a header comment).
                      Read these to understand "what does the database look
                      like right now". Regenerate/edit a table's file whenever
                      a migration changes its shape.

  migrations/        Individual, serially numbered, meant-to-be-run changes,
                      applied in order - e.g. 01_demo_migration.sql,
                      02_next_change.sql. Each one should be idempotent
                      (CREATE ... IF NOT EXISTS / ADD COLUMN IF NOT EXISTS),
                      so re-running an already-applied migration is a safe
                      no-op. Currently empty - the next schema change starts
                      numbering at 01.

  migration.sql      Historical scratch file for one-off consolidated runs.
                      Not part of the numbered migrations/ sequence; leave it
                      empty unless you have a specific reason to consolidate
                      multiple migrations/ files into one script to run by hand.
```

## No migration runner (yet)

There is still no automated migration tool wired into this repo (no
`node-pg-migrate`, no Supabase CLI migrations, nothing that tracks "which
migrations have been applied" in a table). Until that exists, apply changes
manually:

```bash
psql "$DATABASE_URL" -f db/migrations/01_your_change.sql
```

or paste the file into the Supabase SQL editor. Idempotent guards make this
safe to run repeatedly and safe to run against a database that's only
partially migrated.

## Adding a new migration

1. Add a new serially numbered file to `db/migrations/` (e.g.
   `01_demo_migration.sql`, then `02_next_change.sql`), using `IF NOT EXISTS` /
   `ADD COLUMN IF NOT EXISTS` guards so it stays idempotent. Never edit a
   numbered file that has already been applied.
2. Update the matching file(s) in `db/schema/` so they reflect the new
   "current shape" - `db/migrations/*.sql` documents *how you get there*,
   `db/schema/*.sql` documents *what it looks like once you have*. A new
   table gets a new file named after it; a changed table gets its existing
   file edited in place.

## Relationship to `apps/api/database/schema.sql`

That file is a single-file Supabase schema dump, left in place as-is (it may
be regenerated by a dump tool). `db/schema/` is the same information split
into one file per table, kept manually in sync going forward as migrations
land.
